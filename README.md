## Overview

A full-stack URL shortener built on **Cloudflare Workers** (TypeScript) with **Cloudflare D1 (SQLite)** for persistent local storage and a **React + TypeScript** single-page dashboard served via Cloudflare Workers static assets.

---

## How to Run Locally

### Prerequisites
- **Node.js** (v18+ recommended) and **npm**

### 1. Install Dependencies
```bash
npm install
```

### 2. Initialize / Migrate the Local D1 SQLite Database
Apply the SQLite schema (`schema.sql`) to the local D1 database instance managed by Wrangler (`.wrangler/state/v3/d1`):
```bash
npm run db:migrate
# Equivalent to: npx wrangler d1 execute url-shortener-db --local --file=./schema.sql
```

### 3. Build the React Client & Verify TypeScript
```bash
npm run build
npm run typecheck
```

### 4. Start the Local Development Server
```bash
npx wrangler dev
```
> Note: `wrangler.toml` is configured with `[build] command = "npm run build:client"` and `[assets] directory = "./public"`, so `npx wrangler dev` automatically builds the React bundle into `public/app.js` and serves both the React UI and the Worker API on `http://localhost:8787` (or `http://127.0.0.1:8787`).

## Architectural Decisions & What I Prioritized ("Making Reasoning Visible")

### 1. Why Cloudflare D1 (SQLite) Over Workers KV
While Workers KV excels at read-heavy key-value lookups, a URL shortener with analytics and management features has requirements that fit a relational SQLite engine far better:
- **Atomic Click Counter Increments**: Every visit to `GET /:code` must increment the link's click count reliably. In KV, incrementing a counter requires a read-modify-write cycle that is vulnerable to race conditions under concurrent requests and eventual consistency delays. In D1, `UPDATE links SET clicks = clicks + 1 WHERE code = ? AND (max_clicks IS NULL OR clicks < max_clicks) RETURNING *` executes atomically in a single statement.
- **Relational Listing, Filtering, and Sorting**: Displaying a dashboard of links sorted dynamically (`ORDER BY clicks DESC`, `ORDER BY created_at DESC`), filtered by expiration status (`active` vs. `expired`), or searched by substring (`code LIKE ? OR original_url LIKE ?`) is native and indexed in SQLite. Implementing multi-dimensional sorting and filtering in KV would require maintaining fragile secondary index keys or scanning all keys in memory.

### 2. Why a Modular Worker + React Architecture
I prioritized getting a working vertical slice running end-to-end first to validate the D1 binding, SQL schema, and redirect behavior. Once the core flow was verified, I refactored the monolithic single-file Worker into clearly separated backend layers (`src/types.ts`, `src/db.ts`, `src/validation.ts`, `src/routes.ts`, `src/index.ts`) paired with a componentized React frontend (`LinkForm.tsx`, `LinkTable.tsx`, `ErrorAlert.tsx`) bundled with `esbuild` and served via Cloudflare Workers static `[assets]`. This separation keeps every file small, focused, and easy to reason about or extend.

### 3. Strict Server-Side Validation
All validation is enforced on the server in `src/validation.ts`:
- **Protocol Allowlisting (`http:` and `https:` only)**: Parsing candidate inputs with `new URL()` and strictly checking `parsed.protocol === "http:" || parsed.protocol === "https:"` blocks malformed strings as well as dangerous schemes like `javascript:` or `data:` that could introduce XSS vectors.
- **Self-Host Redirect Loop Prevention**: The validator compares the target URL's host (and local aliases such as `localhost` / `127.0.0.1` on the same port) against the Worker's own request host, rejecting self-referential links with `400 Bad Request`.
- **Surfacing Server Validation in the UI**: The React form uses `noValidate` so browser-native HTML5 tooltips do not intercept submissions before they reach the Worker; server-side `400`/`409` JSON error payloads are always exercised and displayed in an accessible `role="alert"` banner.

## What I Added & Why (User Benefit)

### 1. Custom Short Codes & Click-Limit Expiration (`max_clicks` with HTTP `410 Gone`)
- **Why**: Users sharing promotional campaigns, beta invites, or time/usage-limited resources often need human-memorable slugs (e.g., `/launch-2026`) and automatic expiration after $N$ visits.
- **How it works**:
  - `POST /api/links` accepts optional `customCode` (validated against `^[A-Za-z0-9_-]{3,32}$` and checked against reserved routes, returning `409 Conflict` if already taken) and `maxClicks` (positive integer).
  - When a visitor requests `GET /:code` after `clicks >= max_clicks`, the Worker does not increment the counter or redirect; instead, it returns a semantic HTTP `410 Gone` HTML page (distinct from `404 Not Found`) explaining that the link reached its maximum click limit, with a button back to `/`.

### 2. Interactive Analytics Filtering, Click-Count Sorting & Instant Copy
- **Why**: As a user creates more links, a static table becomes difficult to scan. Turning the list into an interactive dashboard makes it easy to identify top-performing links, locate specific URLs, or filter out expired links.
- **How it works**:
  - **Server-Backed Sorting**: `GET /api/links?sort=...` supports `created_desc` (Newest first), `created_asc` (Oldest first), `clicks_desc` (Most clicks), and `clicks_asc` (Least clicks) using an explicit allowlist of SQL `ORDER BY` clauses in `src/db.ts`. Users can sort via the dropdown or by clicking the **Clicks** column header directly.
  - **Status Filtering & Search**: Users can filter by **All**, **Active**, or **Expired** status pills and search by short code or original URL substring.
  - **One-Click Copy**: Both the creation confirmation banner and every row in the table provide a one-click **Copy** button with visual `"Copied!"` feedback.

## How I Tested & Validated the Result

1. **End-to-End UI Testing in `wrangler dev`**:
   - Created links with both auto-generated 6-character alphanumeric codes and custom slugs.
   - Clicked short links from the table, verified the `302` redirect to the destination URL, and confirmed the click count incremented in real time.
   - Restarted `npx wrangler dev` to verify links and click counts persisted across server restarts in local D1 SQLite storage.
2. **Direct Server-Side `curl` Verification (Bypassing the Browser)**:
   - Tested `POST /api/links` with malformed URLs (`not-a-url`), disallowed protocols (`javascript:alert(1)`, `ftp://example.com`), and self-referential URLs (`http://localhost:8787/abc`), verifying `400 Bad Request` JSON responses.
   - Tested duplicate custom codes to verify `409 Conflict` responses.
3. **Redirect & Expiration Status Codes**:
   - Verified `GET /:code` returns `302 Found` with `Cache-Control: no-store, no-cache, must-revalidate` so browsers do not cache redirects and skip click tracking.
   - Verified `GET /nonexistent` returns `404 Not Found` with a human-friendly HTML error page and link back to `/`.
   - Created a link with `maxClicks: 1`, visited it once (`302 Found`, `clicks = 1`), and visited it a second time to verify it returned HTTP `410 Gone`.

## What I Would Do Next With More Time

- **Edge Rate Limiting**: Add Cloudflare Workers Rate Limiting bindings on `POST /api/links` per client IP to prevent automated link-creation abuse.
- **Privacy-Preserving Click Analytics**: Record lightweight click events (timestamp, `request.cf.country`, and referrer hostname) in a secondary `click_events` D1 table using `ctx.waitUntil()` so redirect latency remains near-zero while offering time-series and geographic insights.
- **Automated Integration Test Suite**: Add `@cloudflare/vitest-pool-workers` to run automated unit and D1 integration tests in CI against an isolated Miniflare runtime.
